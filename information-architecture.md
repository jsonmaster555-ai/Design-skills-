# Information Architecture

Information architecture defines how information, features, pages, objects, and actions are organized before visual styling.

Organize around the user's mental model rather than implementation details. Categories should be distinct, labels should predict destinations, and frequently used destinations should remain discoverable.

## Structure

Establish clear parent-child relationships such as Workspace → Project → Files → File. Do not place every feature at the same level.

## Labels and information scent

Prefer specific labels such as `Billing History`, `Manage Members`, and `Security Settings` over vague labels such as `Explore`, `Manage`, or `More` when specificity is possible.

## Navigation

Navigation exposes information architecture; it is not the architecture itself. Separate global navigation, local navigation, and contextual actions. Avoid dumping every feature into a sidebar.

## Progressive depth

Reveal deeper structure when users enter a relevant context. Do not expose the entire product hierarchy simultaneously.

## Search and filters

Search complements architecture but should not compensate for confusing organization. Filters should narrow meaningful dimensions using consistent terminology.

## Testing

Validate architecture through card sorting, tree testing, and usability testing when possible. A strong structure lets users predict where information will be located.
